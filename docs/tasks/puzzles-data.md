# Task: PUZZLE DATA PIPELINE (turn the cache into shippable files)

**You own:** `scripts/build-puzzles.*` (your own script files), `public/puzzles/**` (generated), `src/lib/puzzleData.ts`, `docs/puzzle-data.md`.

## Input
`scripts/.cache/puzzles.jsonl` — 51,920 Lichess puzzles (CC0) already filtered and rating-balanced (one JSON object per line: `id, fen, moves[], rating, themes[], opening, popularity, plays, bucket, kind('theme'|'course')`). See `scripts/build-puzzle-cache.py` for how it was made.
Lichess format: `fen` is BEFORE the opponent's first move; `moves[0]` is the opponent's move; the user then plays `moves[1]`, … (UCI).

## Build
1. A script (Node via `npx tsx`, or Python) that creates **static JSON files under `public/puzzles/`** matching `PuzzleIndex`/`Puzzle` in `src/types.ts`:
   - `public/puzzles/index.json` listing every file (`entries`: key, kind `'theme'|'opening'`, friendly **label**, plain-language **description** (one sentence a beginner understands, e.g. "Fork — one piece attacks two or more enemy pieces at once"), count, file path, min/max rating).
   - one file per **theme** (`public/puzzles/themes/<theme>.json`) and one per **user opening** (`public/puzzles/openings/<courseId>.json` for london / caro-kann / slav, kind `'opening'`, key = the course id), each an array of `Puzzle` objects (drop extra fields; keep `id, fen, moves, rating, themes`, optional `opening`).
   - **Size budget**: whole `public/puzzles` folder ≤ ~9 MB raw (it ships to the user's browser, lazily one file at a time; each file ≤ ~350 KB). Choose per theme ~250–400 puzzles spread over the rating range **400–2000** (more of 600–1600 since the user is ~1100), good popularity, no duplicates across themes needed.
   - Friendly labels for the ~45 themes (e.g. `backRankMate` → "Back-rank mate", `capturingDefender` → "Removing the defender", `intermezzo` → "In-between move (zwischenzug)", `xRayAttack` → "X-ray", `mateIn1` → "Mate in 1", `hangingPiece` → "Free pieces", `quietMove` → "Quiet move", `attackingF2F7` → "Attack on f2/f7", `exposedKing`, …). Drop themes that are not useful for a beginner/club player or merge. Make sure the key themes the app links to exist: fork, discoveredAttack, pin, skewer, backRankMate, capturingDefender, deflection, trappedPiece, mateIn1, mateIn2, hangingPiece.
2. **Verify** every shipped puzzle with chess.js: all moves legal in sequence from `fen`; the final position of the line is plausible (mate or material won) — and run the engine (`scripts/lib/nodeEngine.ts`, depth ~10, only on the first user move; this is 10k+ positions → batch it with a small time budget per position, run in the background, and drop puzzles where the engine's best move at depth ≥ 10 is clearly different from `moves[1]` *and* not equally good (use multipv 2: accept if `moves[1]` is within 30 cp of the best or both are mating). Report how many were dropped.
3. `src/lib/puzzleData.ts`: tiny typed loader used by the UI: `loadPuzzleIndex()`, `loadPuzzles(entry)` (fetch with `import.meta.env.BASE_URL`, cached in memory, helpful errors), `pickPuzzle(puzzles, {targetRating, excludeIds, window})`, and `puzzleToStart(puzzle) -> { startFen (after opponent's first move), solution: string[] (user's moves interleaved with replies), orientation }` (apply `moves[0]` with chess.js).
4. `docs/puzzle-data.md`: where the data comes from (Lichess puzzle database, CC0, https://database.lichess.org/#puzzles), how to rebuild it, licence note.
5. Tell the puzzles-ui builder the final structure in your report (they build the UI concurrently against the contract in `types.ts`; they will read `public/puzzles/index.json` when it appears — **produce `index.json` and 2–3 theme files within your first 10 minutes** so they can start testing, then complete the rest).
