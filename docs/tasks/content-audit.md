# Content audit — independent verification of chess teaching content

You are a strong chess player and a careful editor auditing teaching content written by someone else for **Chess Coach** (read `docs/agent-brief.md` first, especially "Chess-content correctness"). The reader is a ~1100-rated adult learner.
Wrong or misleading chess content is the worst possible bug. Assume the author made mistakes and find them. You own **only the single data file named in your prompt**; fix defects in it directly (minimal, careful edits), keep its structure/exports/ids, keep the plain-friendly-English voice.

## Method (do all of it)
1. **Parse & structure**: run the project's checks (`npx tsx scripts/check-openings.ts` for opening courses; for tactics write a scratch script that loads the lesson with `npx tsx` and applies every move with chess.js). 0 errors required.
2. **Independent engine pass** with a *different* configuration than the author used: `scripts/lib/nodeEngine.ts`, **depth 18**, multipv 3 (go deeper, e.g. depth 20–22 or movetime 4 s, on anything that looks suspicious). 
   - Tactics: for every exercise the user's first move must be the engine's best (or equal-best, or a forced mate that is not slower than the best); every follow-up user move too. Check the *scripted opponent replies* are sensible (flag when they are not the engine's top defence — acceptable only if the explanation covers it). Examples: the demonstrated line must be what the engine would play, and each per-move explanation must be true.
   - Openings: for every position where the user is to move, the recommended move must be within ~50 cp of the engine's best (depth 18) **or** be a long-established, objectively fine theoretical move whose comment doesn't oversell it; every prepared opponent reply flagged as an error (`?`/`?!`) must really be inferior by the engine (≥ ~40 cp), and the punishment shown must work; replies *not* flagged must not be blunders. Compare with the Lichess opening database names (`https://raw.githubusercontent.com/lichess-org/chess-openings/master/{a,b,c,d,e}.tsv`).
3. **Claim check**: read **every sentence** of explanatory text and verify it against the actual board position it is attached to (use chess.js: what attacks what, what is defended, which squares are free, is it check, what is the material count). Typical hallucinations: "attacks the queen" when it doesn't, "the bishop is trapped" when it can escape, wrong move numbers/names of variations/traps/players, "this wins a pawn" when it doesn't, mixing up colours/sides, arrows/highlight squares ([%cal]/[%csl] or `arrows`/`highlights`) pointing at the wrong squares, captions that don't match diagrams.
4. **Teaching quality**: is each idea explained simply and correctly? Is the difficulty ordering sensible? Any jargon unexplained? Any text that would mislead a beginner? Anything unverifiable you cannot confirm → delete or soften it.
5. **Completeness check** (openings): are the main replies at ~1000–1400 level covered? Any gaping hole in a chapter (e.g. a common reply with no answer)? Add missing prepared replies only when you can verify them by the engine; otherwise list them in the report.

## Report (≤ 350 words): positions/sentences checked (counts), defects found (what, where, how fixed), anything left unfixed, overall verdict (ship / ship after listed fixes / not ready).
